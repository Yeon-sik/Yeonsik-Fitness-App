# 범용 운동 이미지 카탈로그 생성 표준

이 문서는 Yeonsik Fitness App의 전체 웨이트 운동을 동일한 제품 언어로 분류하고, 생성하고, 검수하고, 앱에 배포하기 위한 카탈로그 단위 규범이다. 개별 이미지의 세부 제작법은 [IMAGE_GENERATION_STANDARD.md](IMAGE_GENERATION_STANDARD.md)를 함께 따른다.

- 문서 성격: 전체 운동 카탈로그에 적용하는 규범과 확장 계획
- 근거 경계: commit `48cd32f392b1122787832f98107b30e583b96a4e`, 2026-08-25
- 저장소 검증 범위: `Fitness_Weight.json`, 근육 레이어, 기구 catalog, 8개 scene와 16개 프레임, Android 자산 생성 파이프라인
- 한계: 이 문서는 현재 모든 운동 이미지가 완성됐다고 주장하지 않는다. 실기기와 운영 환경도 이번 문서 작성만으로 검증된 것이 아니다.

## 1. 목표

카탈로그는 단순히 340장의 서로 다른 그림을 만드는 작업이 아니다. 다음 다섯 가지를 일관되게 관리하는 제품 시스템이어야 한다.

1. 모든 운동 ID에 시각 자산이 존재한다.
2. 같은 동작 계열은 같은 캐릭터·카메라·기구 언어를 사용한다.
3. 다른 동작은 자세, 기구, 궤도, 근육 활성 차이가 이미지에서 구분된다.
4. 후속 프레임은 확대·축소나 신체 비율 변화 없이 하나의 모션으로 읽힌다.
5. 원본·검수 근거·scene·앱 배포 자산이 다시 생성 가능한 구조로 남는다.

우선순위는 다음과 같다.

```text
운동 식별 가능성
→ 동작·관절·기구의 정확성
→ 주·보조 근육의 정확성
→ 프레임 일관성
→ 미적 디테일
→ 제작 속도
```

## 4. 세 단계 재사용 모델

340개 운동을 모두 텍스트에서 독립 생성하지 않는다. 각 운동은 다음 셋 중 하나로 처리한다.

### 4.1 시각 별칭

다음 항목이 모두 같으면 기존 final PNG를 재사용할 수 있다.

- 동작 궤도와 관절 범위
- 몸의 방향과 지지 방식
- 기구 ID와 `viewId`
- 그립, 스탠스, 벤치 각도, 케이블 시작점
- 편측성 및 작업 측
- 주 활성 레이어 집합과 보조 레이어 집합
- 필요한 프레임 수와 각 프레임의 의미

운동 이름이나 기록 방식만 다르고 시각 정보가 완전히 같을 때만 허용한다. scene은 운동 ID별로 유지하되 같은 final PNG를 참조하고 `generationContract.visualAliasOf`에 원본 운동 ID를 기록한다.

### 4.2 파생 변형

같은 원형이지만 다음 중 하나가 다르면 승인된 골든 프레임을 편집해 별도 final을 만든다.

- 바벨·덤벨·케이블·밴드 등 저항 방식
- 양측·편측
- 그립과 손목 방향
- 플랫·인클라인·디클라인 각도
- 서기·앉기·눕기·엎드리기·매달리기
- 주·보조 근육 레이어
- 기구 접점 또는 이동 궤도

### 4.3 신규 원형

기존 자산으로 동작을 설명할 수 없으면 새 골든 기준 프레임을 만든다. 새로운 카메라 시점이나 머신 시점이 필요하면 운동 이미지보다 기구 자산을 먼저 만든다.

## 5. 렌더링 원형 분류

`motionType`만으로 원형을 정하지 않는다. 현재 데이터에서 `machine_press_seated`는 수평·수직 프레스와 여러 기구를 함께 포함하고, `hip_hinge_motion`은 힙힌지·힙신전·무릎굴곡을 함께 포함한다.

각 운동은 아래 복합 키로 분류한다.

```text
catalogArchetypeId =
  movementPattern
  + supportMode
  + bodyOrientation
  + equipmentKinematics
  + laterality
  + canonicalView
```

필수 렌더링 필드는 다음과 같다.

| 필드 | 예시 | 목적 |
| --- | --- | --- |
| `movementPattern` | `curl`, `horizontal_push` | 기본 관절 동작 |
| `supportMode` | `standing`, `seated`, `supine_bench`, `hanging` | 몸이 어디에 고정되는지 |
| `bodyOrientation` | `upright`, `supine`, `prone`, `hinged` | 몸통 방향 |
| `equipmentKinematics` | `free_weight`, `fixed_path`, `cable`, `band`, `bodyweight` | 저항이 움직이는 방식 |
| `laterality` | `bilateral`, `unilateral` | 좌우 표현 |
| `canonicalView` | `front`, `side`, `front_3q`, `rear_3q` | 판독에 사용할 카메라 |
| `gripVariant` | `supinated`, `neutral`, `pronated` | 손목·전완 차이 |
| `supportVariant` | `chest_supported`, `bench_supported` | 추가 고정 접점 |
| `trajectoryVariant` | `vertical`, `diagonal`, `arc` | 손·발·기구 궤도 |

같은 `motionType`이라도 이 필드가 다르면 별도 원형 또는 파생 변형이다.

## 7. 카메라와 구도 선택

카메라는 예쁜 각도가 아니라 다음 점수를 가장 높이는 각도로 선택한다.

1. 관절 동작과 기구 궤도가 겹치지 않고 보이는가.
2. 주 활성 표층 근육이 실제 노출 범위에서 보이는가.
3. 손·발·좌석·패드·바의 접점이 보이는가.
4. 첫 프레임이 64dp에서도 운동을 구분하는가.
5. 후속 프레임에서 같은 카메라를 유지할 수 있는가.

기본 원칙은 다음과 같다.

- 정면: 좌우 대칭, 컬, 프레스, 레이즈, 내·외전 판독
- 후면: 광배, 승모, 후면 삼각근, 햄스트링, 둔근 판독
- 측면: 힙힌지, 척추 굴곡·신전, 벤치 각도, 무릎·발목 경로 판독
- 3/4: 기구와 신체가 겹치는 복합 동작, 벤치·머신 깊이 표현
- 한 프레임에서 앞·뒤 근육을 동시에 억지로 보여주지 않는다.
- 심층 근육을 보여주기 위해 몸을 투명하게 만들지 않는다. 정해진 심층 투영 규칙을 사용한다.

## 8. 근육 활성도 계약

### 8.1 그룹 계산

```text
primaryLayers = expand(primarySubPart)
secondaryLayers = union(expand(secondarySubParts)) - primaryLayers
```

`overall_*` 그룹이 포함돼도 주 활성 레이어를 보조색으로 덮지 않는다. scene의 `visualContract`에는 그룹과 계산된 레이어를 모두 기록한다. 카메라에서 보이지 않거나 다른 구조에 완전히 가려지는 레이어는 억지로 노출하지 않고 `omittedLayers`에 레이어 ID와 사유를 남긴다.

```text
displayedPrimary = primaryLayers - omittedLayers
displayedSecondary = secondaryLayers - omittedLayers
```

누락 사유 없이 계산된 레이어를 빼거나, 제품 그룹에 없는 레이어를 임의로 추가하면 안 된다.

### 8.2 표시 규칙

- 주 활성 표층: `#ef4444`, 높은 불투명도
- 보조 표층: 같은 빨강 계열의 낮은 불투명도
- 기능 구획: 주황 점선
- 심층 투영: 낮은 불투명도와 해칭·점선
- 건·인대·기준점: 활성 근육으로 집계하지 않음
- 안정근은 동작 이해에 필요한 경우만 보조로 표시
- 편측 운동은 기본적으로 캐릭터 오른쪽을 작업 측으로 정하고 `workingSide`에 기록
- 양측 운동을 편측처럼, 편측 운동을 양측 같은 강도로 칠하지 않음

제품 분류가 해부학 자료와 충돌하면 이미지에서 몰래 바꾸지 않는다. 데이터 오류 후보로 별도 보고한다.

## 9. 기구 카탈로그 규칙

운동보다 기구 원형을 먼저 안정화한다.

### 9.1 재사용 우선순위

1. 같은 기구 ID와 같은 `viewId`를 그대로 합성
2. 같은 기구의 승인된 다른 시점 자산을 새 `viewId`로 등록
3. 기존 기구로 표현할 수 없을 때만 신규 기구 원형 제작

### 9.2 기구별 고정 항목

- 바벨·덤벨·플레이트: 원판 수, 직경, 손잡이 길이, 칼라
- 벤치: 패드 길이·폭·각도, 다리와 바닥 접점
- 케이블: 도르래 위치, 케이블 연결, 손잡이, 웨이트 스택
- 머신: 좌석, 패드, 회전축, 레버, 프레임 폭, 안전 스토퍼
- 밴드: 고정점, 길이, 장력 방향
- 케틀벨: 손잡이와 구체 비율

프레임마다 기구를 다시 생성하지 않는다. 이동 기구는 같은 원본에 강체 변환만 적용하고, 케이블·밴드처럼 변형되는 요소만 경로를 편집한다.

## 10. 프레임 수 결정

| 조건 | 기본 프레임 수 |
| --- | ---: |
| 아이소메트릭, 캐리, 자세 하나로 충분 | 1 |
| 시작과 종료가 필요한 일반 반복 운동 | 2 |
| 중간 궤도가 없으면 오해가 생기는 복합 운동 | 최대 3 |

- 2프레임은 시작·수축 또는 하단·락아웃처럼 의미가 달라야 한다.
- 프레임을 부드럽게 보이게 하려고 같은 자세의 미세 변형을 추가하지 않는다.
- 3프레임은 기구가 몸을 우회하거나 방향이 바뀌는 경우만 사용한다.
- 3프레임을 초과하는 동작은 정적 카탈로그 범위를 넘어선다. 별도 3D·리깅·영상 체계로 분리한다.
- 프레임 일관성을 확보하지 못하면 정적 1장으로 낮춘다.

## 11. 범용 생성 절차

### 단계 A. 데이터 계약

1. 정확한 `exerciseId`를 찾는다.
2. 제품의 모든 분류 필드를 기록한다.
3. 그룹을 실제 근육 레이어로 확장한다.
4. `catalogArchetypeId`와 변형 태그를 정한다.
5. 시각 별칭·파생 변형·신규 원형 중 하나를 선택한다.

### 단계 B. 해부학과 운동역학

1. 해부학 아틀라스·의과대학·의료기관 자료에서 위치와 표층 노출을 확인한다.
2. 공인 운동 지도 또는 운동역학 자료에서 관절 동작, 그립, 궤도, 접점을 확인한다.
3. 서로 독립적인 최소 두 출처를 scene의 `anatomyReview`에 기록한다.
4. 검색 이미지는 스타일 레퍼런스나 복제 원본으로 사용하지 않는다.

### 단계 C. 레퍼런스 패킷

기준 프레임의 입력은 원칙적으로 세 개다.

1. anatomy master: 비율과 근육 경계
2. 같은 원형의 승인 운동 final: 선화, 카메라, 장면 언어
3. 정확한 기구 final: 기구 형상

후속 프레임은 순서가 바뀐다.

1. 승인된 기준 프레임: 편집 대상
2. 정확한 기구 final: 형상 고정
3. anatomy master 또는 승인 원형: 해부학 보조

서로 다른 카메라를 요구하는 레퍼런스를 섞지 않는다. 외부 운동 사진을 네 번째 스타일 이미지로 추가하지 않는다.

### 단계 D. 골든 기준 프레임

1. 첫 프레임 하나만 생성한다.
2. 동작, 근육, 기구, 인체 비율, 알파 경계를 검수한다.
3. 승인 전에는 후속 프레임을 만들지 않는다.
4. 승인 직후 머리·흉골·골반·발·접점·고정 관절 좌표를 scene에 기록한다.

### 단계 E. 파생 프레임

1. 기준 프레임을 첫 번째 편집 대상으로 사용한다.
2. `renderPolicy.animated` 항목만 변경한다.
3. 프롬프트에 좌표와 허용 오차를 수치로 적는다.
4. 실패하면 한 번에 한 항목만 교정한다.
5. 고정 분절 길이, 카메라, 기구 비율이 바뀌면 폐기한다.

### 단계 F. 후처리와 배포

1. 생성 원본을 source에 보존한다.
2. 체크무늬가 구워졌으면 연결 배경 추출 도구로 제거한다.
3. 같은 캔버스와 정규화 변환을 적용한다.
4. final PNG, scene, prompt spec을 함께 저장한다.
5. 감사·자산 검증·Gradle 빌드를 실행한다.

## 12. 운동별 필수 산출물

각 운동은 최소한 다음 파일 관계를 가진다.

```text
exercise-images/source/<exercise>-<frame>-generated.png
exercise-images/final/<exercise>-<frame>.png
exercise-images/scenes/<exercise>.scene.json
exercise-images/scenes/<exercise>.prompt.md
```

scene의 필수 제품 계약은 다음과 같다.

- 정확한 `exerciseId`
- `catalogArchetypeId`와 변형 태그
- 캔버스, 좌표계, 정규화
- 기구 ID 목록
- 고정 앵커
- 프레임 ID, 파일, 시간, 관절 좌표, 이동 기구 변환
- `renderPolicy.locked`와 `renderPolicy.animated`
- `visualContract`: 시점, 작업 측, 주·보조 그룹과 레이어, 금지 강조, 자세 규칙
- `generationContract`: 기준 프레임, 파생 관계, prompt spec, 레퍼런스, source
- `anatomyReview`: 날짜, 출처, 판단 메모

기존 schema가 아직 강제하지 않는 필드는 신규 scene에서 먼저 적용하고 기존 scene은 원형별로 이관한다.

## 13. 검증 게이트

### Gate 1. 데이터 무결성

- 모든 운동 ID가 고유한가.
- scene의 `exerciseId`가 실제 데이터에 존재하는가.
- 주·보조 그룹이 모두 `exerciseGroups`에 존재하는가.
- scene의 기구 ID가 catalog에 존재하는가.
- 시각 별칭이 실제로 같은 레이어·자세·기구 계약을 갖는가.

### Gate 2. 해부학·동작

- 주 활성 근육의 위치와 표층 노출이 맞는가.
- 보조 근육이 주 활성보다 진하지 않은가.
- 심층 근육과 건을 표층처럼 칠하지 않았는가.
- 관절 각도와 궤도가 운동을 식별하기에 충분한가.
- 손목, 팔꿈치, 무릎, 척추가 비현실적으로 꺾이지 않았는가.
- 기구 접점과 저항 방향이 연결돼 있는가.

### Gate 3. 단일 프레임 시각 품질

- 캐릭터 스타일이 승인 원형과 같은가.
- 얼굴·의복·문자·로고·그림자가 없는가.
- 손가락·발가락·사지 수가 정상인가.
- 기구 형상과 원판 수가 승인 자산과 같은가.
- 모든 필수 요소가 잘리지 않았는가.
- 첫 프레임이 64dp에서 구분되는가.

### Gate 4. 프레임 일관성

- 캔버스와 카메라가 같은가.
- 고정 앵커 오차가 긴 변의 0.5%, 1536px 기준 약 8px 이내인가.
- 고정 기구 크기 변화가 1% 이내인가.
- 고정 기구 회전 변화가 0.5도 이내인가.
- 머리 크기, 몸통 폭, 고정 분절 길이가 달라지지 않았는가.
- 전환 시 확대·축소·좌우 점프가 보이지 않는가.

### Gate 5. 파일·앱

- source와 final이 모두 존재하는가.
- final이 실제 알파 PNG인가.
- 모든 프레임이 scene 캔버스와 같은가.
- prompt spec과 모든 상대 경로가 존재하는가.
- manifest 검증이 통과하는가.
- Gradle이 최대 768px·256색 배포 PNG를 생성하는가.
- Java catalog에 정확한 운동 ID와 프레임 시간이 생성되는가.

### Gate 6. 실기기

- 목록 첫 프레임이 작게 표시돼도 식별되는가.
- 상세에서 프레임이 잘리지 않는가.
- 1초 전환이 자연스러운가.
- 애니메이션 정지·탭 일시정지가 동작하는가.
- 빌드 통과와 실기기 검증을 별도 상태로 보고했는가.

## 15. 340개 확장 순서

### 15.1 전체를 한 번에 생성하지 않는다

운동을 같은 원형·시점·기구로 묶어 5~10개 단위로 작업한다. 한 묶음에서 골든 원형 하나를 먼저 승인하고 나머지는 시각 별칭 또는 파생 편집으로 만든다.

### 15.2 우선순위

1. 데이터 감사와 원형 분류
2. 현재 없는 핵심 기구·시점 자산
3. 21개 motionType의 대표 골든 원형
4. 기구·그립·지지 방식 변형
5. 편측·특수 자세·심층 근육 운동
6. 모든 scene의 강화 메타데이터 이관
7. 전체 커버리지 게이트

`motionType` 대표 21개가 곧 최종 원형 21개라는 뜻은 아니다. 복합 키가 다르면 더 많은 원형이 필요하며 정확한 개수는 전체 분류 후 확정한다.

### 15.3 변경 묶음

하나의 작업 브랜치 또는 PR은 가능한 한 같은 원형을 공유한다.

- 같은 카메라와 지지 방식
- 같은 기구 또는 기구 계열
- 같은 고정 앵커
- 같은 검수 관점

이미지, scene, prompt spec, 필요한 기구 자산, 검증 결과를 함께 제출한다.

## 16. 실패 처리

- 텍스트만 바꿔 재생성하지 않는다. 실패 원인을 카메라·관절·기구·근육·배경 중 하나로 분류한다.
- 한 번에 하나만 교정한다.
- 기준 프레임이 틀렸으면 후속 프레임을 모두 폐기하고 기준부터 다시 승인한다.
- 기구가 흔들리면 캐릭터와 기구를 다시 한 번에 생성하지 말고 기구 합성과 앵커를 수정한다.
- 배경 제거가 흰색 인체를 지우면 자동 결과를 승인하지 않는다.
- 2프레임 기준을 못 맞추면 1프레임으로 낮춘다.
- 데이터 분류 오류는 이미지로 숨기지 않고 데이터 변경 후보로 보고한다.

## 17. 카탈로그 Definition of Done

전체 카탈로그 완료는 다음 조건을 모두 만족할 때만 주장한다.

- [ ] 감사 도구가 현재 `Fitness_Weight.json`의 모든 운동을 집계한다.
- [ ] `--require-complete`가 성공한다.
- [ ] 모든 운동 ID에 scene이 하나씩 존재한다.
- [ ] 모든 scene의 주·보조 그룹과 기구 ID가 유효하다.
- [ ] 모든 신규 scene이 강화된 시각·생성·해부학 계약을 가진다.
- [ ] 모든 final PNG가 실제 투명 배경과 동일 캔버스 규격을 가진다.
- [ ] 시각 별칭, 파생 변형, 신규 원형의 근거가 기록돼 있다.
- [ ] 모든 동적 scene이 앵커·기구·카메라 기준을 통과한다.
- [ ] 전체 manifest 검증과 `testDebugUnitTest assembleDebug`가 통과한다.
- [ ] 실기기 표본 검수 범위와 결과가 별도로 기록돼 있다.
- [ ] 미검수 외부 동작이나 운영 상태를 완료로 표현하지 않는다.
